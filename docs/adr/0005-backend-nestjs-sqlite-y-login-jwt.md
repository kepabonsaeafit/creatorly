# ADR-0005: NestJS backend with SQLite and JWT login

- **Date:** 2026-10-04
- **Status:** Accepted — supersedes ADR-0001 (persistence in LocalStorage)
- **Decided by:** Kevin Pabón (architect)

## Context

"Deliverable 1 Part 2" asks to add a backend project as a folder of this repository, remove the seeders and the store elements that no longer apply from the frontend, make the frontend read its data from the backend's database, and implement a working login (guided by https://docs.nestjs.com/security/authentication).

The professor's reference project (https://github.com/danielgara/courseprojects-2026, folders `backend/` and `frontend/`) is the style the course grades: NestJS with TypeORM on SQLite, one folder per resource, plain DTO classes, numeric ids, and a frontend whose services call the API with axios. The first backend version in this repo (branch `integrating-backend-with-login-system`) used PostgreSQL through Docker, UUID ids and class-validator, which departs from that reference.

## Decision

- **Backend in `backend/`**, NestJS 12 (ESM), following the professor's `backend/` structure file by file. The frontend stays at the repository root.
- **SQLite** through `better-sqlite3` and `TypeOrmModule.forRoot({ type: 'better-sqlite3', database: process.env.SQLITE_PATH ?? 'database.sqlite', autoLoadEntities: true, synchronize: true })`, written directly in `app.module.ts`, as the professor does. No Docker, no `.env` for the database.
- **Numeric ids** generated by the database (`@PrimaryGeneratedColumn()`). The frontend interfaces change `id: string` to `id: number`, and `utils/generateId.ts` disappears: the frontend no longer creates ids.
- **Relations** of `Order` with `Brand`, `Creator` and `User` use `@ManyToOne` + `@JoinColumn` + `@RelationId`, the same shape as the professor's `Review` → `Book`. The API keeps returning `brandId`, `creatorId` and `userId`, so the frontend still references by id.
- **Validation in the service**, not in the DTO: DTOs are plain classes (`CreateOrderDto`), like the professor's, and each backend service validates and throws `BadRequestException` / `NotFoundException`. `class-validator` and `class-transformer` are removed.
- **Login with JWT**, following the NestJS authentication guide: `AuthModule` with `AuthService.signIn`, `POST /api/auth/login` returning `{ access_token }`, a global `AuthGuard` and a `@Public()` decorator for the login route. Passwords are stored hashed with `bcrypt`, never in plain text and never returned by the API.
- **Seeders move to the backend**: each module has a `*.seeder.ts` that inserts the demo data when its table is empty. The frontend has no seeders.
- **Frontend**: entity stores, seeders, `PiniaConfig` hydration/persistence and `generateId` are removed. Services become `async` and use axios with `private static readonly API_URL = \`${import.meta.env.VITE_API_BASE_URL}/api/<resource>\``. `StorageService` survives only to keep the session token, so no module touches `localStorage` directly. `SessionStore` is the only store left.

## Considered Options

- **PostgreSQL with Docker** — rejected: it departs from the professor's reference and forces every team member, and the professor when grading, to run Docker.
- **UUID ids** — rejected: the professor uses numeric ids; with a database generating them, the reason that justified UUIDs in ADR-0001 (no coordination in the browser) no longer exists.
- **class-validator + ValidationPipe** — rejected: the professor does not use it, and it would split the rule "validations live in the service" across two places.

## Consequences

- The database file `backend/database.sqlite` is created on first start and ignored by git.
- Every request except `POST /api/auth/login` needs the header `Authorization: Bearer <token>`.
- Filters and chart aggregations stay as pure static methods of the frontend services, applied to arrays fetched from the API.
- The "Reset demo data" button disappears: deleting `backend/database.sqlite` and restarting the backend re-seeds it.
